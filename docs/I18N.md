# Internationalisation (i18n) — how translation works and how to extend it

Broward Trading ships in English and Spanish. This document explains the mechanics (`js/i18n.js`, `i18n/es.json`, `course/es/`), how to add a third language, how to keep the Spanish in step when the English changes, and how the structure validator catches mistakes before they reach students.

The design goal was **no page rewrites**: every HTML file and every UI module stays authored in English, and a translation is a data file. That keeps the "no build step, plain ES2020" rule, lets a bilingual student contribute a translation by editing JSON, and means a missing translation degrades to English instead of to a blank.

## 1. Two layers: interface and course

| Layer | What it covers | Where the translation lives | Mechanism |
|---|---|---|---|
| **Interface** | Nav, buttons, labels, table headers, toasts, signal reasons, order ticket, settings, placeholders, `title` and `aria-label` attributes, every string a UI module builds in JavaScript | `i18n/<code>.json` (one file per language; Spanish is `i18n/es.json`, 2,700+ entries) | `js/i18n.js` (`BT.i18n`) swaps exact English strings in the live DOM and translates JS strings through `BT.t()` |
| **Course** | Modules and lessons, quizzes, drills, glossary, Daily 5 question bank, module index, First Week | `course/<code>/<same filename>.json` (Spanish is `course/es/`) | `js/course.js` loads `course/<lang>/x.json` and falls back to `course/x.json` per file, flagging `englishOnly:true` |

The two layers are independent: the interface can be fully Spanish while a module is still English (it shows an "English only" badge), and vice versa.

## 2. How the interface is translated

### The dictionary

`i18n/es.json`:

```json
{
  "_meta": { "lang": "es", "label": "Español", "version": "0.4.0", "entries": 2742 },
  "ui": {
    "Dashboard": "Panel",
    "Buy": "Comprar",
    "Bought {qty} {symbol} @ {price}": "Compraste {qty} {symbol} @ {price}",
    "Free educational simulator. No real orders, no real money.": "Simulador educativo gratuito. Sin órdenes reales, sin dinero real."
  },
  "attrs": {
    "Dismiss": "Cerrar aviso"
  }
}
```

- **Keys are exact English strings**, trimmed and with internal whitespace collapsed to single spaces (`BT.i18n.norm()`). Case matters. `"Buy"` and `"buy"` are different keys.
- `ui` is consulted for text nodes and, as a fallback, for attributes. `attrs` is consulted first for `placeholder`, `title`, `aria-label` and `alt`, for the rare case where an attribute needs a different wording than the same text in a button.
- `{name}` placeholders are literal and must appear in the translation; `BT.t()` fills them after translating.
- `_meta` is informational. `entries` is maintained by hand and is not checked.
- The brand name "Broward Trading" is never a key; it is the one string that stays as is in every language (the validator enforces this).

### The DOM walker

On load and after every language switch, `BT.i18n.translatePage(root = document.body)`:

1. Walks every text node. For each, it normalises the text, looks it up in the active dictionary and, on a hit, replaces the node's text and stores `{orig, out, lang, gen}` on the node (`node.__bt`; attributes use `el.__btA[name]`) so that switching back to English restores it exactly, including the original whitespace. `document.title` is handled the same way.
2. Does the same for the four attributes above on every element.
3. Skips `<script>`, `<style>`, `<code>`, `<pre>`, `<kbd>`, `<textarea>`, `<svg>`, anything inside `.no-i18n` or `[translate="no"]`, and never touches the *value* of an input, so what a student typed is never rewritten.
4. Tags each translated node with the current dictionary generation so a second pass is O(1) per already-translated node.

A **MutationObserver** on `document.body` (debounced about 40 ms) runs the same pass on inserted nodes, so toasts, rendered tables, lesson blocks and the order ticket translate as they appear. The observer discards the mutations caused by its own writes.

### JavaScript strings

UI modules build many strings in code (`'Bought ' + qty + ' ' + sym`). Those cannot be found by the DOM walker if they are assembled after the fact, and concatenated strings would never match a dictionary key anyway. The rule is:

```js
// English stays the source text; vars are named, never concatenated
toast(BT.t('Bought {qty} {symbol} @ {price}', { qty: 10, symbol: 'AAPL', price: fmtMoney(190) }));
```

`BT.t(str, vars)` looks `str` up (normalised) in the active dictionary, falls back to `str` itself, then interpolates `{vars}`. In English, `BT.t` is a passthrough plus interpolation, so English output is byte-identical to code that never knew about translation.

`js/nav.js` injects `js/i18n.js` before a page's own scripts when the page has not included it, so `BT.t` exists on every page. When `BT.i18n` is somehow absent, modules use a local `T()` shim that interpolates and returns English.

### Formatting

`BT.i18n.fmtNumber`, `fmtMoney`, `fmtPercent` and `fmtDate` wrap `Intl` with the active locale (`en-US`, `es-419`) and never throw: bad input yields an em dash (`—`) or the input string. Use them for anything a student reads; keep raw `toFixed()` for data that goes back into the engine. Daily bar `time` strings (`'YYYY-MM-DD'`) are accepted by `fmtDate`.

### Persistence and caching

- The choice is stored in `localStorage` key `bt.lang` as a JSON string (`"es"`); English removes the key. Bare legacy values are read too; anything that is not a known code is ignored.
- A fetched dictionary is cached in `bt.i18n.<code>` so that on the next page load it is registered **synchronously** before the page's own scripts run. That is why `BT.t()` translates toasts from the first render instead of after a network round trip. The cache record carries a content hash (`BT.i18n.hashDict`, FNV-1a over the `ui` and `attrs` tables); the background refresh compares that hash, not `_meta`, so a corrected translation reaches returning users even when `_meta.version` and the entry count did not change.
- `BT.i18n.fmtMoney` uses `currencyDisplay: 'narrowSymbol'`, so Spanish prints `$1,234.50` like the pages' own `money()` helpers, never `USD 1,234.50`.
- User-authored text is never machine-translated: wrap it in `.no-i18n` / `translate="no"`, or mark the element `data-user-text`; elements being edited in place (`contenteditable`) are skipped too.
- `<html lang>` is set to the active code. Screen readers switch voice; CSS can use `:lang(es)` for the few places Spanish needs more room.

## 3. How the course is translated

`course/es/` mirrors `course/` **file by file with the same filename**:

```
course/
├── index.json               ← English
├── m1-foundations.json
├── m9-crypto-etf.json
├── drills.json
├── glossary.json
├── questionbank.json
├── firstweek.json
└── es/
    ├── index.json           ← Spanish, same ids, same module order
    ├── m1-foundations.json  ← same lesson ids, same block order, same quiz answer indexes
    └── …                    ← anything missing here falls back to English
```

`BT.course.fileFor('m1-foundations.json', 'es')` → `course/es/m1-foundations.json`. `fetchLocalised(name)` tries the translated file first and the English one on any error (404, bad JSON), returning `{json, lang, englishOnly}`. The index, every module, the glossary, drills and question bank each carry `lang` and `englishOnly`, and `learn.js` renders a small **English only** pill where `englishOnly` is true. When the Spanish index exists but a module file does not, the index row for that module learns `englishOnly:true` after the first load attempt.

**What must stay identical in a translated course file**

- `id` of the module and of every lesson; the lesson **order**.
- The number and order of `blocks` in each lesson, and each block's `type`.
- In `quiz` blocks: the number of questions, the number of choices, and every `answer` index. Translate the question and the choices; never reorder them (the index is the answer).
- `chart` blocks: `symbol`, `interval`, `overlays`; translate only `caption`.
- `exercise` blocks: `action.page` and `action.hash`; translate only `md`.
- `drill` blocks: `drillId`.
- Glossary: `id` and `related` keys; translate `term`, `definition`, `example`. `[[term]]` references inside lesson text use the glossary **id** when the English term is not Spanish-friendly: `[[rsi]]` works in both; the glossary's `term` field is what the tooltip displays.
- Question bank: `id`, `lessonId`, `answer`.
- `firstweek.json`: `id` of days and tasks, every `check`, every `link.href`.
- `minutes` may stay as in English.

Why so strict: progress, quiz scores, drill results, classroom snapshots and the certificate are all keyed by these ids. A student who switches language mid-course keeps everything, and an instructor's gradebook does not care which language a quiz was taken in.

**Markdown subset** (`BT.course.renderMd`) is the same in every language: paragraphs, `**bold**`, `*italic*`, `- lists`, `### headings`, inline `code`, `[[glossary term]]`. HTML in `md` is escaped, so a translation cannot inject markup.

## 4. Switching language

- Students: **EN / ES** toggle in the top nav (desktop) or the More sheet (phones). It calls `BT.i18n.setLang(code)`.
- `setLang` persists the choice, sets `<html lang>`, loads the dictionary if needed (`i18n/<code>.json`), re-translates the page, and dispatches `bt:lang` on `window` with `{detail: {lang}}`.
- `js/course.js` listens for `bt:lang` (and the older name `bt:langchange`), switches its own language, drops its caches, and `learn.js` re-renders the current view so the lesson reloads from `course/es/`. A language switch during an in-flight load resolves with the new language; the cache never holds stale data.
- Pages that render once (dashboard, portfolio) need nothing: the DOM walker handles the static parts and `BT.t` handles the dynamic ones.
- Programmatic: `BT.i18n.lang()` → `'en' | 'es'`, `BT.i18n.next()` → the next entry in `BT.i18n.langs`, `BT.i18n.info(code)` → `{code, label, short, locale}`.

## 5. Writing translatable code

For contributors touching HTML or JS:

1. **Write English in the markup and in code.** Never write Spanish in a page.
2. **Keep strings whole.** `'Order ' + status` cannot be translated. Use `BT.t('Order {status}', {status})` and translate `status` separately if it is user-facing.
3. **Do not translate data.** Symbols, ids, contract codes, numbers from the engine, and anything that goes back into localStorage stay raw. Wrap them in `<code>` or `.no-i18n` when they appear in the DOM so the walker leaves them alone; the walker already skips inputs' values.
4. **Attributes count.** `placeholder`, `title`, `aria-label`, `alt` are translated from `attrs` then `ui`. Other attributes are not.
5. **Match the dictionary's exact text.** Changing `"Review order"` to `"Review your order"` in HTML silently drops the Spanish for that button. Section 6 explains the workflow.
6. **Numbers and dates** through `BT.i18n.fmt*` for display.
7. **Pluralisation** is by template: `BT.t('{n} trades', {n})` and, where English needs it, two keys (`'1 trade'`, `'{n} trades'`) chosen in code. Spanish plurals follow the same split. There is no plural-rule engine; keep it simple.
8. **Test in both.** Switch to ES, open the page, look for English leftovers (they are easy to spot) and for layout overflow at 390 px. Spanish runs 15 to 30 % longer than English; buttons that were tight in English break first.

## 6. Updating Spanish when English changes

The dictionary is keyed by exact English text, so **any change to an English UI string is a change to a dictionary key**. The workflow:

### When you change or add an English string in HTML or JS

1. Make the English change.
2. Open `i18n/es.json` and search for the **old** English text. If it is there, rename the key to the new English text and update the Spanish if the meaning changed. If it is not, add a new entry.
3. Keep `{placeholders}` identical in key and value.
4. Run `node tests/i18n.test.js` (checks normalisation, placeholders, no empty values, the smoke list of core strings).
5. If the string is user-visible and you cannot write the Spanish, add the key with the English text as a temporary value **and** say so in the pull request, so a translator sees it. A missing key is fine too (English shows), but an entry makes the gap searchable: `grep -n '": "\1"'` style equality checks find keys whose value equals the key.

### Finding English that has no Spanish yet

There is no extraction tool (no build step), so the practical audit is to run the site in Spanish and look. A lighter check from the command line, listing visible text in a page that is not a dictionary key:

```bash
# crude: pulls text between tags in a page, normalises whitespace, and lists lines absent from es.json
node -e '
const fs=require("fs");const es=JSON.parse(fs.readFileSync("i18n/es.json","utf8")).ui;
const norm=s=>s.replace(/\s+/g," ").trim();
const html=fs.readFileSync(process.argv[1],"utf8").replace(/<script[\s\S]*?<\/script>|<style[\s\S]*?<\/style>/g,"");
const seen=new Set();
for (const m of html.matchAll(/>([^<>{}]{3,})</g)) { const t=norm(m[1]); if (t && !/^[\d\W]+$/.test(t) && !es[t] && !seen.has(t)) { seen.add(t); console.log(t); } }
' learn.html
```

Treat the output as a to-do list, not gospel: it includes template fragments and demo data.

### When you change a lesson in `course/`

- **Wording only** (a sentence, a callout, a caption): the Spanish file is now behind. Either update `course/es/<file>.json` in the same change or note it in the PR under a "Spanish behind" heading. The validator will not catch wording drift; only humans do.
- **Structure** (a new question, a reordered choice, a new block, a new lesson): you **must** make the same structural change in `course/es/<file>.json` or delete that Spanish file (so the module falls back to English with the badge) until it is re-translated. `node tests/course-v04.test.js` fails otherwise, and CI blocks the deploy.
- **New module**: add it to `course/index.json`; add it to `course/es/index.json` with Spanish `title` and `summary` and the same `id`, `level`, `minutes` and lesson ids. The module body can follow later.
- **Glossary term added**: add it to `course/es/glossary.json` with the same `id`; otherwise the Spanish glossary lacks the term and the tooltip falls back to English through `BT.course.glossary`'s fallback.
- **Drill or question added**: same `id` in the Spanish file.

### Release checklist for translations

- [ ] `node tests/i18n.test.js` and `node tests/course-v04.test.js` pass.
- [ ] Open every page in Spanish at 390 px; no English leftovers in the shell, the order ticket, the signal panel, the course home, the instructor page.
- [ ] `i18n/es.json` `_meta.version` matches the release and `_meta.entries` is roughly right.
- [ ] `docs/CHANGELOG.md` names the modules translated in this release and the ones still English only.

## 7. Adding a language

Haitian Creole (`ht`) is the next planned language; the steps are the same for any code. Use a BCP 47 code: `ht`, `pt-BR`, `fr`.

1. **Register the language.** In `js/i18n.js`, add to the `LANGS` array:
   ```js
   { code: 'ht', label: 'Kreyòl Ayisyen', short: 'HT', locale: 'ht' }
   ```
   `label` is shown in the More sheet, `short` on the nav toggle, `locale` is passed to `Intl`. If `Intl` lacks data for the locale, formatting falls back to the browser default, which is acceptable. (`BT.i18n.addLang()` does the same at runtime and is what tests use; shipping a language means editing the array.)
2. **Create the dictionary.** Copy `i18n/es.json` to `i18n/ht.json`, keep every **key**, replace every **value**, set `_meta`. Start with the shell and the order ticket: `tests/i18n.test.js` lists the strings every dictionary must have (`Dashboard`, `Learn`, `Buy`, `Sell`, `Review order`, `Order filled`, the disclaimer footer line, the signal reasons). Untranslated keys may be deleted; English shows for them.
3. **Create the course folder.** `course/ht/index.json` first (titles and summaries, same ids). Then module files in the order students meet them: `m1`, `m2`, `m4` (risk), `m3`, `m7`, `m9`, `m5`, `m6`, `m8`; then `glossary.json`, `drills.json`, `questionbank.json`, `firstweek.json`. Every file follows section 3's identity rules.
4. **Validate.** Generalise the two tests: `tests/i18n.test.js` reads `i18n/es.json` by name; add a loop over `fs.readdirSync('i18n')` (or a second block for `ht.json`) so the same assertions run for every dictionary. `tests/course-v04.test.js` compares `course/es/*.json` with `course/*.json`; parameterise `esDir` over every subfolder of `course/`. Keep the assertions identical; only the paths change.
5. **Service worker.** Add `i18n/ht.json` and `course/ht/*.json` to the precache list in `sw.js` and bump `VERSION`, so the language works offline on an installed phone.
6. **Nav.** Nothing to do: `js/nav.js` reads `BT.i18n.langs` and renders a toggle (in the top nav and in the More sheet) whose short codes are listed in order and which cycles to the next registered language on each tap. With three or more languages, check that the short codes still fit the 44 px button at 390 px; if not, show only the current code in the top nav and the full list in the sheet.
7. **Docs.** Add the language to README "Languages", this file, `docs/TEACHING_GUIDE.md` section 13 and the changelog.
8. **Right-to-left** languages would additionally need `dir="rtl"` on `<html>` (set it next to `<html lang>` in `setLang`) and a CSS pass; nothing in the current layout has been checked for RTL.

A language is considered **shipped** when the dictionary covers the shell, dashboard, course home, lesson reader, portfolio and replay pages, and at least Modules 1 to 4 of the course are translated. Partial languages can live on a branch or behind `addLang()` until then.

## 8. The structure validator

There is no separate validation script yet (one is on the roadmap); the validators are two of the unit tests, which run on every push in CI and block the deploy when they fail.

### `tests/i18n.test.js` — the dictionary

| Check | Why it matters |
|---|---|
| `i18n/es.json` parses; `ui` and `attrs` are objects | A broken file would make the whole interface stay English with no error visible to students |
| At least 900 `ui` entries | Guards against an accidental truncation or a partial file being committed |
| Every key equals `BT.i18n.norm(key)` | Keys with leading / trailing / double spaces can never match a DOM string |
| Every value is a non-empty string | An empty value would blank out a button |
| Every `{placeholder}` in a key appears in its value, and vice versa | `BT.t()` fills placeholders after translating; a dropped `{symbol}` loses the symbol from the toast, an added one leaves `{foo}` on screen |
| At least 100 templated keys exist | Confirms the JS-string layer is translated, not only the static markup |
| A smoke list of core strings is present (shell, order ticket, toasts, signal reasons, disclaimer footer) | These are the strings a Spanish-speaking student sees in the first minute |
| `"Broward Trading"` is **not** a key | The brand name is never translated |
| Module behaviour: `norm`, `interpolate`, `lookup` with `attrs` preference, `setLang` persistence and events, `addLang`, `stored()` safety, `Intl` formatters, 2,000 lookups under 50 ms | The pure parts of the walker, testable without a DOM |
| `nav.js` reads `BT.i18n.langs`; the toggle markup carries `no-i18n` | The language names themselves must not be translated |

### `tests/course-v04.test.js` — the course mirror

For every `course/es/m*.json` that exists, against `course/m*.json` of the same name:

| Check | Why it matters |
|---|---|
| Same module `id` | Progress and the index are keyed by it |
| Same lesson ids in the same order | `lessonsDone`, `quizScores`, deep links, classroom snapshots |
| Same quiz `answer` indexes per lesson, in order | A reordered choice would mark Spanish students wrong (or right) for the wrong reason |

The same file also tests the loader's behaviour with virtual files: translated file first, English fallback with `englishOnly:true`, index rows learning that a module is English only, caches dropping on `bt:lang`, and no stale data after a switch during a load. If `course/es/` does not exist, the mirror test is skipped, which is why the folder can be added file by file.

### Running them

```bash
node tests/i18n.test.js
node tests/course-v04.test.js
# everything, as CI does:
for t in tests/*.test.js; do echo "== $t"; node "$t" || exit 1; done
# JSON sanity for every translated file
for f in i18n/*.json course/es/*.json; do [ -f "$f" ] && node -e "JSON.parse(require('fs').readFileSync('$f','utf8'))" || echo "BAD JSON: $f"; done
```

### What the validator does not check

- Wording drift (English changed, Spanish did not). Humans and the changelog.
- Block counts and types inside lessons, chart symbols, exercise hashes, glossary `related` keys. These are worth adding to the mirror test when `course/es/` has content; the loop in `tests/course-v04.test.js` is the place.
- Layout overflow in Spanish at 390 px. The Playwright e2e script can take a Spanish screenshot set once `setLang('es')` is added to its flow.

## 9. Style guide for Spanish

The Spanish is **neutral Latin American** (`es-419`), written for South Florida students whose families come from many countries.

- **Tú**, not usted and not vos. The English is second person and friendly; keep that.
- Keep established market English where Spanish-speaking traders use it: *trading*, *paper trading* (explain once as "operar con dinero simulado"), *stop* / *orden stop*, *spread*, *bid / ask* (with "compra / venta" on first use), *backtest*, *replay*, *swing*, *scalping*, *ETF*, *RSI*, *MACD*. Translate the rest: *media móvil*, *soporte y resistencia*, *velas*, *tamaño de la posición*, *drawdown* becomes *caída máxima* with "drawdown" in parentheses the first time in a lesson.
- Numbers and money through `Intl` (`1.234,50` vs `1,234.50` is the formatter's job, not the translator's). Keep `$` and USD; the course is about US markets.
- The disclaimer and honesty lines are translated as faithfully as possible, not softened: "Sin órdenes reales, sin dinero real", "Los precios demo son simulados", "Describe lo que dicen los indicadores ahora; no predice el futuro".
- Lengths: a Spanish button label should fit the same 44 px tap target; prefer *Comprar* / *Vender* over longer forms; use abbreviations the UI already uses in English (`SMA`, `P&L` becomes `G/P` or stays `P&L` where the column is narrow).
- No regionalisms that change meaning across countries (*plata*, *coger*, *carro* vs *coche*); use *dinero*, *tomar*, *auto* where they come up.
- Glossary definitions: one or two sentences, same structure as English, same example symbol.

## 10. Known limits

- Exact-match translation cannot handle a sentence that the page splits across elements (`<b>Buy</b> 10 shares`). Each fragment is translated on its own; most read fine, some need the markup changed so the sentence is one node.
- Strings that differ only by trailing punctuation are separate keys (`"Buy"` vs `"Buy."`).
- The walker does not translate `<option>` text inside a `<select>` that a script rebuilds every tick; add those labels through `BT.t()` in the script.
- Spanish for the **course** is added module by module, so a student sees "English only" badges until the folder is complete. The badge is deliberate honesty, not a bug.
- No locale-aware sorting in tables (`localeCompare` with the active locale is a small follow-up).
- Certificate text (`certificate.html`) accepts `?lang=` so an instructor can print a Spanish certificate for a student who worked in Spanish; the verification page shows the stored name and course in the language it was issued.

## 11. Quick reference

| Task | Where |
|---|---|
| Add or change a UI string | Edit English in HTML / JS; update the key and value in `i18n/es.json`; `node tests/i18n.test.js` |
| Translate a JS-built string | `BT.t('Template with {vars}', {vars})`; add the template to `i18n/es.json` |
| Keep something untranslated | Wrap in `<code>` or add class `no-i18n` / `translate="no"` |
| Translate a module | Copy `course/<file>.json` to `course/es/<file>.json`, translate text, keep every id / answer / symbol / hash; `node tests/course-v04.test.js` |
| Add a language | `LANGS` in `js/i18n.js`; `i18n/<code>.json`; `course/<code>/`; generalise the two tests; `sw.js` precache + `VERSION`; docs |
| Format a number / date for display | `BT.i18n.fmtNumber`, `fmtMoney`, `fmtPercent`, `fmtDate` |
| Read or set the language in code | `BT.i18n.lang()`, `BT.i18n.setLang('es')`, listen for `bt:lang` on `window` |
| Storage keys | `bt.lang` (choice), `bt.i18n.<code>` (cached dictionary) |
